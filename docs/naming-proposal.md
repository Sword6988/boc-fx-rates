## 一、程序命名方案

### 1.1 为什么「外汇现汇买入价查询」不再合适

1. **反向换算下「买入价」语义不成立**：反向视图「1 人民币 = X 外币」是现汇买入价取倒数的结果，既不是任何官方挂牌价名目（中行没有「人民币兑外币的买入价」这种牌价），用户复制出去用于换算时叫「买入价」会误导。
2. **PEN 数据源名不副实**：秘鲁新索尔中行不挂牌，走 open.er-api 市场参考汇率（中间价），与「现汇买入价」是两类口径，卡片上还标着「● 备用源参考」。
3. **产品定位升级**：程序已从「单向查牌价」变为「双向汇率换算」，名称只描述了旧功能的一半，且「查询」二字没有覆盖「换算」。
4. **名称过长**：8 字 + 「查询」共 10 字，exe 名「外汇现汇买入价查询.exe」在桌面和任务栏都显得冗长。

### 1.2 当前名字出现的位置（已逐一核实）

| 文件 | 位置 | 内容 |
|---|---|---|
| `config.py:16` | `APP_TITLE` 常量 | 窗口标题（`app.py:900`）、托盘提示（`app.py:966`）、弹窗（`app.py:1595`）、**单实例互斥量与 FindWindowW（`app.py:2106-2122`）**、配置目录名、调试日志文件名（`app.py:2064-2065`）全部由它派生 |
| `app.py:1003` | 界面内品牌标题 | 「外汇现汇买入价」（无「查询」二字） |
| `build.ps1:6` | `$appName` | 码点数组拼出 exe 名 |
| `version_info.txt:19-24` | FileDescription / InternalName / OriginalFilename / ProductName | 均为旧名 |
| `.github/workflows/ci.yml:44,51` | CI 打包 --name 与附件名 | 旧名 |
| `README.md` / `index.md` | 标题与 `%APPDATA%` 路径说明 | 旧名 |

⚠️ **改动牵连提示（给工程师）**：`APP_TITLE` 同时是单实例互斥量名和 FindWindowW 窗口匹配名。改名后，若用户旧版 exe 仍在运行时启动新版，两者互不感知会并存两个实例——属一次性过渡现象，可接受，无需处理。

### 1.3 三个候选名

| # | 窗口标题 | exe 文件名 | 英文标识（ProductName / 目录可用） | 理由 | 配置目录迁移风险 |
|---|---|---|---|---|---|
| 1 | **中行汇率换算** | `中行汇率换算.exe` | `BocFxConverter`（目录沿用中文名亦可） | 点名数据源（中行牌价是本工具唯一差异化卖点，与仓库名 boc-fx-rates 一致）+「换算」覆盖双向新功能；6 字窄标题栏完整显示 | 需迁移（见 1.4） |
| 2 | 汇率换算助手 | `汇率换算助手.exe` | `FxRateHelper` | 中性安全、无品牌关联顾虑；「助手」贴合桌面小工具气质 | 需迁移（同上） |
| 3 | 汇率速查 | `汇率速查.exe` | `FxRateQuick` | 最短（4 字），窄标题栏最从容 | 需迁移（同上） |

**不推荐的方向**：任何含「现汇买入价」的名字（语义已不成立）；含「双向」的名字（如「双向汇率换算」——「双向」是实现细节不是用户价值）；纯英文/拼音名（目标用户是查中行牌价的中文用户，桌面 exe 中文名更友好）。

### 1.4 推荐：**中行汇率换算**

**取舍理由**：
- 三要素齐备：数据源（中行）× 功能（汇率换算）× 体量感（小工具）。候选 2、3 都丢掉了「中行」——而这正是用户在众多汇率工具里选它的理由（官方牌价、可信）。
- 「换算」比「查询/速查」准确覆盖了双向切换这一新核心能力。
- 6 字标题在窄标题栏完整可见；exe 名放桌面清晰不拗口。
- 「中行」属描述性使用（数据来源说明），README 已明确数据来自中国银行官网、非官方工具，风险可接受。

**配套改名（落地时同步）**：
- 界面内品牌标题 `app.py:1003`：`外汇现汇买入价` → `中行汇率换算`；副标题 `中国银行外汇牌价 · 现汇买入价 / 市场参考汇率` **保留不动**（它准确描述的是数据来源口径，不是产品名）。
- 调试日志文件名（`app.py:2064-2065`）→ `中行汇率换算_debug.log`。
- `build.ps1` 的 `$appName` 码点数组重算；`version_info.txt` 四个字段；`ci.yml`；`README.md` / `index.md` 同步。

### 1.5 配置目录处理：**改名 + 一次性自动迁移**（推荐）

- **方案 A（推荐）**：目录名跟随新名 `%APPDATA%\中行汇率换算`。启动时若新目录 `config.json` 不存在而旧目录 `%APPDATA%\外汇现汇买入价查询\config.json` 存在 → 读取旧配置写入新目录，成功后尝试删除旧目录（失败静默，下次不再迁移因新配置已存在）。
  - 理由：配置仅 3 个字段（选中币种 / geometry / inverse），丢失成本≈0，而迁移代码约 15 行、风险≈0；做了用户完全无感，不做则旧名永远留在用户 %APPDATA% 里，与产品名不一致，且未来解释成本高。
  - 兜底：旧配置读取失败按默认值处理——现有 `_load_config` 已是防御式实现，天然兼容。
- **方案 B（零风险备选）**：目录继续沿用旧名「外汇现汇买入价查询」→ 修改 `_config_dir()` 硬编码路径与 `APP_TITLE` 解耦即可。适合想把这轮改动压缩到最小的情形；缺点是名实永久不符。
- **不推荐**：只改目录不迁移（老用户的币种选择、窗口位置、换算方向全部静默丢失）。

## 二、切换按钮文案方案

### 2.1 现状确认（代码核实）

- `app.py:133-136`：`DIR_TEXT_FWD = "⇄ 外币→人民币"` / `DIR_TEXT_REV = "⇄ 人民币→外币"`，注释明确「文案即当前方向 + 刻意等长防按钮宽度跳动」。
- `_build_direction_toggle`（1651-1666）：一行 = 左标签「换算方向」+ 右按钮（`pack side="right"`），按钮 `padx=14`，9px 字体。
- `_render_dir_button`（1668-1692）：按 `_inverse` 换文案与配色；`_toggle_direction`（1694-1708）只重算展示、不重新抓取。

### 2.2 同类软件调研结论

| 参考对象 | 方向切换控件 | 文案模式 | 图标 | 状态 vs 动作 |
|---|---|---|---|---|
| **XE Currency**（网页/App） | 位于 From/To 两个币种选择器**中间**的圆形按钮 | **无文字，纯图标** | 上下双向箭头（swap 图标） | 动作（点击即对调）；当前方向由两侧币种字段本身呈现 |
| **Google 汇率换算**（搜索小组件） | 两个币种字段中间的交换按钮 | 无文字，纯图标 | 双向交换箭头 | 动作；状态在等式两端字段里 |
| **极简汇率 xCurrency** | 两个货币行之间的交换按钮 | 无文字，纯图标 | 交换箭头（「点选交换的按钮也能直接更换兑换的国家货币」） | 动作 |
| **中行/工行手机银行** 汇率换算 | 无切换按钮：用「基准币种/目标币种」两个下拉选择双向换算；牌价类型（现汇买入/卖出价）用分段选择器 | 文字型（下拉/分段控件） | 无 | 状态由选择器当前值直接呈现 |

**行业共性总结**：
1. 主流做法是**纯图标动作按钮**，且放在被对调的两个对象的中间——因为**当前方向永远由紧邻的 From/To 字段直接可见**，按钮无需再表达状态。
2. 没有发现任何主流产品在按钮上写「切换后的目标方向」。
3. 上下双向箭头（⇅/swap）出现在「上下堆叠」布局；左右等式布局用左右双向箭头（⇄/⇌）。

**与本程序的关键差异**：本程序的对调对象是卡片里的横向等式「1 外币 = 数值 人民币」，按钮**不在**等式中间而在其上方独立一行，且卡片会滚动出视口——此时固定的按钮行是唯一可见的方向指示。因此**不照搬纯图标动作式**，保留状态式文案更贴合本程序布局（这是与 XE/Google 结论表面相反、实则同一原则「状态要可见」的落地）。

### 2.3 四个决策点——明确结论

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 按钮写「当前方向」还是「下一步动作」？ | **当前方向**（维持现语义，仅美化措辞） | ① 卡片滚出视口后按钮是唯一方向指示；② 左标签「换算方向」+ 状态文案构成自然的「标签：值」读法；③ 业界动作式成立的前提（From/To 字段紧邻按钮）在本程序不成立。若未来把按钮移进卡片等式中间，再改纯图标动作式 |
| 2 | `⇄` 还是 `⇅`？ | **`⇄`（U+21C4）** | 卡片是横向等式，切换 = 等式左右两侧对调，左右双向箭头语义精确；`⇅` 适合上下堆叠的 From/To 布局（XE 移动端那样），与本程序不符。**字形已实测**（见 2.5） |
| 3 | 保留左侧「换算方向」标签？ | **保留** | 按钮独立成行，无标签时裸按钮语义悬空；标签为低频用户提供「这是什么控件」的锚点；宽度成本仅 48px（实测），该行空间充裕。不并入按钮（并入后要么文案过长、要么丢失「方向」语境） |
| 4 | 两态文案必须等长吗？ | **保持等长（强约束）** | 虽然按钮 `pack side="right"`、跳动只表现为自身左缘移动，不会挤压同行控件，但等长可彻底消除切换瞬间的按钮尺寸跳变（视觉抖动），且现文案天然等长、维持等长零成本，没有理由放弃 |

### 2.4 字形兼容性实测（tkinter + GDI 双重验证）

在 Microsoft YaHei UI 下用 GDI `GetGlyphIndicesW`（GGI_MARK_NONEXISTING_GLYPHS）检测 + Tk 真实渲染截屏目视确认：

| 符号 | YaHei UI 字体内 | Tk 实际渲染 | 结论 |
|---|---|---|---|
| `⇄` U+21C4 | ✗ 无字形 | ✅ 正常（经 Windows 字体链接回退到 Segoe UI Symbol，9px/28px 均清晰） | **可用**（现版本已在用，实测无豆腐块） |
| `⇅` U+21C5 | ✗ 无字形 | ✅ 正常（同样字体链接回退） | 可用，但语义不如 ⇄，不采用 |
| `↔` U+2194 | ✗ 无字形 | ⚠️ 9px 下渲染成近似一条短横线，形状不可辨 | **不可用**（小字号不可辨形） |
| `→` U+2192 | ✓ 有字形（idx 0x0252） | ✅ 正常 | 可用 |
| `⇆ ⇋ ⇌ ⇔ ⇕` U+21C6/21CB/21CC/21D4/21D5 | ✗ | （同字体链接机制，理论可用） | 不采用：无增益 |
| `₽` U+20BD（卡片在用） | ✗ | 字体链接可显示 | 与本方案无关，仅提示 |

**结论**：`⇄` 与 `→` 组合安全可靠，无需更换符号体系。（注：`⇄` 依赖 Windows 字体链接而非字体自带字形，Win10/11 标准环境均含 Segoe UI Symbol，风险极低；且为现版本既有符号，无回归风险。）

### 2.6 推荐：**组 A**

落地字符串（直接替换 `app.py:133-136`）：

```python
DIR_TEXT_FWD = "⇄ 外币 → 人民币"
DIR_TEXT_REV = "⇄ 人民币 → 外币"
```

- 仅在 `→` 两侧各加一个半角空格，其余一字不动；两态 95px 等长，按钮宽度恒定。
- 左标签「换算方向」、⇄、配色、交互逻辑均不动。
- 状态栏切换提示（`app.py:1705`「已切换：1 人民币 = X 外币」）与卡片等式文案不受影响，无需改动。
